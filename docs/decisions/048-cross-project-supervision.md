# ADR-048 — Cross-project supervision and explicit target scope

- Status: accepted
- Date: 2026-09-16

An imported definition remains immutable. Schema 21 adds append-only operator adoption of
its complete scheduling proposal set, bound to the exact plan-binding revision with an
actor and rationale. Adoption authorizes the source's enumerated early-development rules;
it does not pass plan, architecture, technical, qualification or publication checkpoints.
Those checkpoints retain their independently reviewed evidence requirements. Adoption,
roadmap creation and Start are separate authenticated commands.

A cross-project roadmap is an ordinary delegated roadmap with an additional frozen map
configuration. The server computes the selected milestone closure, including phase
inheritance, original parent barriers and evidence producers. Target-only selection excludes
later obligations without accepting or waiving them. Full selection retains all milestones
and orders the target ancestors first. The preview shows both sets; no suggested target is
selected automatically. One delegated roadmap per workspace remains the authority boundary.

Generate development, verification and parent-acceptance activities from that closure.
Effective settings resolve defaults → project → activity → individual; overrides replace a
complete settings set. Started attempts keep their original definition revision and profiles,
including parent-acceptance delegation. Edits only change queued settings. Cross-map scope or
binding changes require a new roadmap until the reviewed amendment workflow exists.

Verification and acceptance reuse supervised cycles in review-only mode: independent review,
existing timeouts, bounded background-result recovery and explicit restart resumption. They
cannot run implementation/remediation on a review snapshot. Findings or questions pause for
operator recovery through the owning scope. Clean review snapshots refresh with fast-forward
only, then receive a fresh review; normal development updates still use integration merges.
Review admission uses verification resources, not development capacity. Recording evidence
uses the shared current-code, current-generation, qualified-review and ancestry gates, with
controller delegation rechecked before the receipt commits. Parent acceptance defaults to
manual and can be explicitly delegated; protected final promotion cannot.

Completion requires every selected milestone, including accepted target checkpoint evidence,
with external Git freshness rechecked. Show target reached, selected scope complete, all
parents accepted, plans finalized and publication separately. Newly invalidated completed
verification requires an explicit new review rather than silent history rewrites. The operator can
use Review again on a completed review cycle: it retains the attempt’s frozen reviewer assignment,
fast-forwards its idle clean snapshot, and creates a new run with the previous review as its parent.
Prior runs and receipts remain immutable; current phase gates and receipt checks still apply. Native/Kata
qualification remains externally executed and explicitly reviewed. Aggregate eligible
checkpoint reminders through the existing durable notification outbox; ordinary dependency
and resource waits are not attention events.

Operator-designated agent reviewer responsibilities are explicit settings, bound to the attempt's
saved revision and recorded on scope receipts. They are responsibilities under the existing trusted
agent model, not authentication of a human maintainer or a sandbox qualification. The exact supervised
review run must match the assigned backend/model/permission profile and report all scope evidence.
Assignments do not bypass resource authorization, native/Kata execution boundaries or checkpoint
attestations; qualified external reviews remain available.
