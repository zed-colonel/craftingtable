# CT-02 — Persistent daemon, authentication, workspaces, and durable event history

**Risk:** High  
**Dependencies:** CT-01  
**Status:** Proposed for operator approval  
**Source baseline:** `693445257d61222959c2efa9fc82c621fa8c6653` (`CT-01: record remediation review and completion`)  
**Primary areas:** storage, authentication, sessions, workspaces, authorization, audit, snapshots, SSE replay

## 1. Objective

Turn the accepted CT-01 executable skeleton into a persistent, authenticated local daemon whose browser state can be reconstructed after refresh, disconnect, or daemon restart.

CT-02 must establish the durable foundation on which every later CraftingTable capability depends:

- one authoritative SQLite database;
- one bootstrap administrator and default workspace;
- server-side authenticated sessions;
- explicit workspace membership and service-layer authorization;
- append-only audit history with attributable actors;
- append-only, monotonically sequenced workspace events;
- transactionally consistent workspace snapshots;
- authenticated SSE replay and live delivery;
- browser reconstruction from snapshot plus subsequent events;
- restart-safe local operation.

CT-02 does **not** implement projects, plan import, repositories, worktrees, real agents, verification, reviews, or merge operations. It establishes the durable control plane those later work items will use.

## 2. Governing statement

> The daemon commits authoritative state before the browser can observe it. The browser reconstructs a projection from an authenticated snapshot and a durable event cursor; it never becomes a source of truth.

## 5. Fixed implementation decisions

The following decisions are part of this work contract unless the operator accepts a written change before implementation.

### 5.1 Persistence adapter

Use `better-sqlite3` behind a new `@craftingtable/storage` package.

Rationale:

- CraftingTable is a low-concurrency, single-daemon local application;
- the synchronous transaction API makes state + audit + event atomicity straightforward;
- the library is mature, supports full transactions, and recommends WAL mode;
- Node 24's built-in `node:sqlite` remains release-candidate rather than fully stable;
- a driver interface is unnecessary at this stage, but SQLite-specific use must remain inside `@craftingtable/storage`.

Add `better-sqlite3` and its required build permission to the pnpm workspace configuration. Add TypeScript declarations if the package version requires them.

### 5.2 Migration strategy

Use ordered SQL migration files managed by a small repository-owned migration runner.

The runner must:

- maintain `schema_migrations` with version, name, checksum, and application time;
- apply unapplied migrations in ascending order;
- reject a changed checksum for an already-applied migration;
- reject a database whose schema version is newer than the application supports;
- run each migration in an explicit transaction where SQLite permits it;
- fail startup without partially applying a migration;
- be testable against temporary database files.

Do not introduce an ORM or general migration framework in CT-02.

### 5.3 Database operating mode

The storage package must configure and verify at least:

```text
PRAGMA journal_mode = WAL
PRAGMA foreign_keys = ON
PRAGMA synchronous = FULL
PRAGMA busy_timeout = 5000
```

The database and its `-wal`/`-shm` companions are one persistence unit. Documentation must warn against copying only the main file while it is open. Backup and restore commands remain CT-08 scope.

### 5.4 Password hashing

Use the `argon2` package with Argon2id and its maintained secure defaults unless measurement on the pinned workstation demonstrates that bounded parameter adjustment is necessary.

Passwords must never be:

- stored in plaintext;
- written to logs, audit metadata, error messages, command history, or process arguments;
- returned by an API;
- accepted through a public registration endpoint.

Add the native package to pnpm's approved build dependencies.

### 5.5 Session model

Sessions are opaque, server-side records.

- Generate at least 256 bits of cryptographically random token material.
- Send the raw token only in the session cookie.
- Store only a SHA-256 digest of the token in SQLite.
- Use a generic cookie name that can be upgraded to a `__Host-` name when HTTPS becomes mandatory in CT-08.
- Set `HttpOnly`, `SameSite=Strict`, `Path=/`, and an explicit expiry.
- Set `Secure` whenever the configured public origin is HTTPS; CT-02 itself remains loopback HTTP.
- Support logout and explicit revocation.
- Reject expired and revoked sessions.
- Never place session tokens in URLs, logs, SSE payloads, or audit metadata.

A practical initial absolute lifetime is 30 days. A different lifetime may be proposed during Phase A if it is structurally configured and tested.

### 5.6 CSRF model

Authenticated state-changing HTTP requests require a synchronizer token bound to the active server-side session and sent through a custom request header.

- The token may be returned as part of the authenticated session response.
- The token must never be placed in a URL.
- Compare tokens using a timing-safe operation.
- Mutating routes must reject missing or invalid tokens.
- Login must accept JSON only and reject cross-site browser origins or fetch metadata; it must not be usable as a simple cross-site form submission.
- `SameSite=Strict` is defense in depth, not the sole CSRF control.

A maintained Fastify CSRF plugin may be used only if it cleanly supports the custom server-side session model and the exact behavior is covered by tests. Do not adopt `@fastify/session` merely to satisfy a plugin integration.

### 5.7 Workspace authorization

Every workspace-owned command or query must authorize membership in the service layer. UI filtering is never authorization.

Define roles now:

```text
Owner
Editor
Viewer
```

Only `Owner` needs an active creation or mutation path in CT-02. The schema must not assume one workspace or one user.

Users and sessions are principal-scoped rather than artificially workspace-owned. Workspace-domain rows, event queries, and workspace audit queries must carry a `WorkspaceId`.

### 5.8 Event vocabulary

Replace the CT-01-specific `AgentEventEnvelope` as the primary live wire type with a workspace-scoped `WorkspaceEventEnvelope` or equivalently clear name.

The durable envelope must contain:

```text
id
sequence
occurredAt
workspaceId
kind
payload
optional actorUserId
optional projectId
optional workItemId
optional runId
schemaVersion
```

Rules:

- `sequence` is assigned by the database, never by a backend or browser;
- the sequence is monotonically increasing across the durable journal;
- every event is immutable after insertion;
- every event is filtered by authorized workspace before delivery;
- raw vendor events never enter this journal directly;
- audit records remain a separate semantic record type;
- CT-01's per-connection fake sequencing is removed from the authoritative runtime.

The first durable kind vocabulary may be very small. It must include enough to render the bootstrapped workspace honestly. Do not invent future Git, plan, review, or agent semantics in CT-02.

### 5.9 State, audit, and event atomicity

A successful state-changing domain command must commit, in one SQLite transaction where applicable:

```text
state-table mutation
+ append-only audit record
+ zero or more workspace events
```

The implementation may expose a small transaction helper. Do not build a generic command bus, event-sourcing framework, or workflow engine.

Authentication-only events may produce audit records without workspace events. Workspace-domain changes should identify the workspace in both audit and event records.

### 5.10 Snapshot and replay

The browser reconstructs a workspace using:

```text
authenticated session query
    ↓
authorized workspace list
    ↓
transactionally consistent workspace snapshot
    + asOfSequence
    ↓
SSE connection requesting events after asOfSequence
    ↓
ordered replay
    ↓
live tail
```

The snapshot and its `asOfSequence` must represent one consistent database view. An event committed after that snapshot must be delivered through replay or the live tail. No event may be lost in the transition between querying the journal and waiting for the next notification.

The SSE endpoint must:

- be authenticated;
- be workspace-scoped;
- accept an initial `after` cursor;
- honor a valid `Last-Event-ID` header on native reconnection;
- validate and serialize shared contracts;
- emit ordered events exactly once per connection cursor;
- retain heartbeat comments;
- periodically revalidate session validity or otherwise terminate promptly after revocation;
- remain correct after daemon restart because replay comes from SQLite, not process memory.

Duplicate delivery across network failure is acceptable only if the browser reducer is idempotent by event sequence or ID. Lost delivery is not acceptable.

## 7. Bootstrap administrator

Add a CLI path equivalent to:

```text
pnpm craftingtable admin bootstrap --username keith
```

The exact root script may differ if documented, but the operation must:

- run against the same configuration and migration path as the daemon;
- refuse to place the password in command-line arguments;
- prompt for the password twice without echo;
- create the first user, default workspace, and `Owner` membership atomically;
- append attributable system/bootstrap audit records;
- append a durable workspace-created event;
- fail without mutation if a user already exists;
- avoid any public self-registration route.

The core bootstrap service must be testable without an interactive terminal.

## 8. Required HTTP surface

The exact route names may be adjusted during the accepted Phase A plan, but the target semantics must include:

```text
GET  /api/health

POST /api/auth/login
GET  /api/auth/session
POST /api/auth/logout
GET  /api/auth/sessions
POST /api/auth/sessions/:sessionId/revoke

GET  /api/workspaces
GET  /api/workspaces/:workspaceId/snapshot
GET  /api/workspaces/:workspaceId/events?after=<sequence>  # SSE
GET  /api/workspaces/:workspaceId/audit?limit=<n>&before=<sequence>
```

Requirements:

- all response and request bodies have shared Zod contracts;
- authenticated responses use `Cache-Control: no-store` where sensitive;
- unauthenticated access receives a generic `401`;
- unauthorized workspace access must not leak another workspace's existence;
- mutating authenticated routes require valid CSRF protection;
- route handlers remain thin and delegate authorization and persistence to services.

CT-02 need not expose workspace creation, invitations, role management, or user creation through HTTP.

## 9. Browser behavior

Replace the simulated CT-01 startup path with an authenticated durable flow.

The browser must:

- show a login form when no valid session exists;
- use a typed API client over shared contracts;
- load the current user and active session;
- list authorized workspaces;
- select a workspace without assuming only one can ever exist;
- hydrate from a workspace snapshot;
- open the workspace SSE stream after the snapshot cursor;
- apply events idempotently and in sequence;
- preserve visible state across refresh;
- reconnect after a transient daemon outage;
- show a clear authentication-expired state when appropriate;
- support logout;
- expose enough session management to revoke another current user's session record;
- display durable workspace activity honestly;
- remove the normal-runtime implication that data is simulated.

Do not add a routing framework unless the accepted Phase A plan demonstrates a concrete need. Conditional authenticated/unauthenticated application shells are sufficient.

## 10. Audit requirements

Audit records are not ordinary activity events.

Each state-changing or security-relevant action must record, where applicable:

```text
audit ID and monotonic sequence
time
actor kind
actor user ID
session ID
workspace ID
command/action name
target type and target ID
outcome
request/correlation ID
prior version or hash
resulting version or hash
safe structured metadata
```

At minimum, audit:

- bootstrap success and refusal;
- login success and failure without exposing password or session material;
- logout;
- session revocation;
- workspace-domain mutations created by bootstrap;
- authorization denial for a workspace command where useful and safe.

Audit rows are append-only. Database-level protections must reject update or delete attempts in normal operation.

The audit query endpoint must authorize workspace membership. Principal-level authentication events may be queryable only by the owning user or an appropriate future administrator path; CT-02 may limit the UI to workspace audit history.

## 11. Persistence location and configuration

Use an XDG-compatible default rooted under:

```text
${XDG_DATA_HOME:-$HOME/.local/share}/craftingtable
```

At minimum:

```text
state/craftingtable.sqlite
```

Support a typed `CRAFTINGTABLE_DATA_DIR` override for tests and explicit development environments.

Requirements:

- create the data directory with owner-only permissions where the platform permits;
- create the database with owner-only permissions;
- never commit development databases, WAL files, or session material;
- tests use isolated temporary directories;
- normal tests never touch the operator's real database;
- shutdown closes the database cleanly after active HTTP/SSE work has stopped.

## 12. Package and dependency boundaries

Add `@craftingtable/storage` as the only package that imports the SQLite driver.

Recommended direction:

```text
contracts  → domain
storage    → domain
server     → domain + contracts + storage
web        → domain + contracts
```

More precisely:

- `domain` remains pure and has zero runtime dependencies;
- `contracts` owns wire schemas and depends on `domain`;
- `storage` owns SQLite schema, migrations, transactions, and repository implementations; it may depend on `domain` but should not depend on Fastify or React;
- server services own authentication, authorization, command orchestration, snapshots, and stream coordination;
- routes own HTTP adaptation only;
- web owns projections and interaction state;
- `testing` may own temporary storage factories and test fixtures but may not become production composition.

Do not create a separate package for every service. Add a package only at a real dependency, security, or reuse boundary.

- transaction rollback leaves no partial state, audit, or event record;

- event sequence remains monotonic across reopen;
- snapshot reads a consistent cursor and state;

### 14.3 Authentication and authorization tests

Cover:

- bootstrap success and second-bootstrap refusal;
- Argon2id password hash and verification;
- generic invalid-login response;
- session token is not stored in plaintext;
- cookie attributes;
- expiry and revocation;
- logout;
- CSRF rejection and acceptance;
- cross-site login protections;
- missing membership denial;
- cross-workspace access denial without existence leakage;
- role vocabulary exists while only Owner is activated;
- secrets do not appear in logs or audit metadata.

### 14.4 Snapshot, SSE, and replay tests

Cover both orderings around the replay/live boundary:

```text
snapshot → event commit → SSE connect
SSE connect → event commit
```

Also cover:

- `after` query cursor;
- `Last-Event-ID` reconnect cursor;
- ordered replay;
- no duplicate visible projection after refresh;
- server restart with the same database;
- browser reconnect after temporary outage;
- invalid event cannot reach the browser projection;
- unauthorized SSE is rejected;
- workspace filtering;
- session revocation or expiry terminates or invalidates the stream;
- a notification occurring between a journal query and waiter registration is not lost.

### 14.5 Process and browser acceptance tests

At minimum:

1. create a temporary data directory;
2. bootstrap a user and workspace through the real service/CLI path;
3. start the daemon;
4. log in through the browser;
5. display the persistent workspace and activity;
6. refresh without duplicating or losing events;
7. stop and restart the daemon against the same database;
8. use the existing session or log in again according to the accepted session policy;
9. reconstruct the same workspace state;
10. log out and prove protected APIs are no longer accessible.

The E2E harness must not reuse an unrelated stale server.

## 16. Acceptance criteria

CT-02 is complete only when all of the following are true:

1. A clean data directory migrates to the current SQLite schema.
2. The bootstrap command creates exactly one user, one default workspace, and one Owner membership atomically.
3. A second bootstrap attempt fails without mutation.
4. The bootstrap user can log in through the browser.
5. Passwords use Argon2id and never appear in storage or logs as plaintext.
6. Session cookies and server-side session records satisfy the contract.
7. Logout and session revocation invalidate access.
8. Authenticated mutations require valid CSRF protection.
9. Workspace queries and streams enforce membership in the service layer.
10. Every workspace-owned record introduced in CT-02 carries a `WorkspaceId`.
11. Audit records identify the responsible user/session where applicable and remain append-only.
12. Workspace events are durable, append-only, database-sequenced, and workspace-filtered.
13. State mutation, audit, and related workspace events commit atomically.
14. The browser hydrates from a transactionally consistent snapshot with an `asOfSequence` cursor.
15. SSE replays every authorized event after that cursor in order and then tails live events without a lost-wakeup race.
16. Refresh does not duplicate or lose visible events.
17. A temporary daemon outage produces visible reconnect/disconnected state and later recovery.
18. Daemon restart against the same database preserves user, workspace, session policy, audit, event, and snapshot state.
19. The daemon remains impossible to bind to a non-loopback interface in CT-02.
20. No CT-03-or-later feature is implemented.
21. `pnpm check` passes under the repository-managed Node `24.18.0` runtime.
22. The completion report lists changed files, commands, decisions, deferred work, and unresolved risks.

The machine-readable acceptance IDs in `work-items/CT-02-acceptance-matrix.yaml` are part of this contract.

## 18. Stop and escalate conditions

Stop before implementation or during a generation and request operator direction when:

- the accepted source baseline differs from `693445257d61222959c2efa9fc82c621fa8c6653` in a material way;
- implementing an acceptance criterion requires CT-03-or-later scope;
- a new major framework, ORM, auth platform, or state-management library appears necessary;
- the proposed design would expose the daemon off-loopback;
- session, CSRF, or workspace authorization semantics cannot be made explicit and testable;
- SQLite state, audit, and event records cannot share one reliable transaction boundary;
- a browser-facing stream would depend on per-process memory for correctness;
- a migration or native dependency cannot run reproducibly under Node `24.18.0` on the target workstation;
- the implementation would preserve CT-01 fake runtime behavior as a competing source of truth;
- an agent proposes changing this contract, acceptance criteria, or architecture without operator approval.
