# CT-03 — Import plan bundles and render the project/work-item dashboard

**Risk:** Medium  
**Dependencies:** CT-02  
**Status:** Proposed for operator approval  
**Source baseline:** `c8e2396a65466bdde95bf740771af63b4fc2272e` (`docs: fix typo in CT-02 remediation review filename`)  
**Primary areas:** planning import, projects, plan versioning, work items, dependency analysis, dashboard, manual admission, work-contract drafts

## 1. Objective

Extend the accepted CT-02 durable control plane so CraftingTable can ingest a structured planning bundle, preserve its source material, validate its work graph, present it visually, and let an authenticated operator admit a proposed work item into a non-executable draft contract.

The first acceptance workload is the actual AQ-CONT-1 planning bundle included with this package.

CT-03 must establish:

- durable `Project`, `PlanBundle`, `PlanVersion`, `PlanArtifact`, `PlanImportAttempt`, `PlanImportDiagnostic`, `WorkItem`, `WorkItemDependency`, and `WorkContractDraft` records;
- a pure planning-import boundary that parses, validates, normalizes, and diagnoses plan inputs without depending on Fastify, React, SQLite, or process control;
- immutable, content-addressed plan versions;
- preservation of every accepted source artifact and every unknown source field;
- actionable diagnostics for malformed, inconsistent, or cyclic plans;
- workspace-scoped, service-authorized import and query paths;
- project, plan-version, and work-item browser views;
- honest readiness, risk, dependency, blocker, and attention summaries;
- manual admission of a proposed work item;
- automatic creation of an explicitly incomplete, non-executable work-contract draft;
- post-commit workspace-event notification through the CT-02 daemon notifier;
- refresh, reconnect, and daemon-restart reconstruction from SQLite.

CT-03 does **not** register source repositories, run Git, create worktrees, invoke coding agents, execute checks, approve work contracts, or merge code.

## 2. Governing statement

> A planning bundle proposes a durable agenda. Import preserves and validates the proposal; it does not silently activate work, infer missing authority, or execute anything.

## 4. Accepted CT-02 foundation

CT-03 must extend, not bypass, these accepted properties:

- one loopback-only persistent Fastify daemon;
- one authoritative SQLite database;
- ordered checksum-verified migrations;
- strict package direction:
  - `domain → none`;
  - `contracts → domain`;
  - `storage → domain`;
  - `server → domain + contracts + storage`;
  - `web → domain + contracts`;
- dependency-injected server composition;
- Argon2id authentication and digest-backed server sessions;
- session-bound CSRF and origin/fetch-metadata checks;
- service-layer workspace membership authorization;
- append-only audit and workspace-event journals;
- state, audit, and related event writes committed atomically;
- a global monotonic workspace-event cursor with permitted cross-workspace gaps;
- snapshot-first browser reconstruction followed by replay and live tail;
- browser-side runtime validation of all wire payloads;
- no production dependency on fake agent or Git packages;
- no ActionQueue, WorldInterface, or Exoskeleton runtime dependency;
- `pnpm check` under the pinned Node runtime as the full local gate.

The accepted CT-02 review contains one binding forward handoff:

> Every daemon-side CT-03 command that appends a workspace event must call the composed daemon notifier after its transaction commits, and acceptance coverage must prove delivery without waiting for the one-second fallback poll.

## 5. Fixed implementation decisions

The following decisions are binding unless the operator approves a written amendment before implementation.

### 5.1 Import transport

Use an authenticated multipart HTTP request for CT-03 plan import.

Do not accept ZIP archives in CT-03.

Reasons:

- the initial bundles are small and already exist as discrete files;
- multipart preserves named artifacts without archive extraction;
- avoiding ZIP handling avoids path traversal, decompression-bomb, duplicate-entry, and archive-normalization complexity;
- Planning Studio can later write the same artifact model directly.

The import endpoint must:

- require an authenticated workspace member;
- require `Owner` or `Editor` role;
- require a valid session-bound CSRF token;
- reject cross-site browser origins through the existing policy;
- reject duplicate logical filenames within one request;
- reject filenames containing path separators, NUL, or invalid normalized names;
- enforce bounded file count, per-file size, and total request size;
- keep raw bytes and content type separate from parser interpretation;
- never interpret a client filename as a host filesystem path.

Initial limits:

```text
maximum files:          12
maximum bytes per file: 2 MiB
maximum total bytes:    8 MiB
```

A source-grounded Phase A plan may propose smaller limits. Increasing them requires explicit approval.

Required logical artifacts:

```text
one implementation-plan Markdown file
one work-breakdown YAML file
```

Optional accepted artifact classes:

```text
Markdown
YAML
JSON
plain text
checksum manifest
```

The importer must identify the required roles through explicit form fields or an unambiguous manifest, not by guessing from prose.

### 5.2 Planning package boundary

Add a pure package named `@craftingtable/planning` or an equivalently clear boundary.

It owns:

- bundle-input types;
- work-breakdown YAML parsing;
- source-schema validation;
- normalization;
- identifier validation;
- required and recommended dependency analysis;
- cycle detection;
- diagnostics;
- canonical content digest input;
- draft-contract projection from a normalized work item.

It must not import:

- Fastify;
- React;
- SQLite or `better-sqlite3`;
- filesystem APIs;
- process control;
- agent SDKs;
- Git;
- CraftingTable server or browser internals.

It may depend on:

- `@craftingtable/domain`;
- a YAML parser;
- Zod where runtime schema validation is useful.

The existing `contracts` package remains the owner of HTTP/SSE wire schemas. The planning package must not become a second HTTP-contract package.

### 5.3 Supported work-breakdown profile

CT-03 supports the current Exo Stack-style work-breakdown profile used by the AQ-CONT-1 fixture.

The normalized importer must require:

```text
document
pull_requests
```

Each work item must require at least:

```text
id
title
depends_on
risk
primary_areas
exit_gate
```

The importer may normalize and expose optional recognized fields, including:

```text
repository
baseline_commit
contract
stack_revision
phase
status
clean_break
integration_branch
tag
release_order
forbidden_release_symbols
recommends
```

Unknown fields must not be discarded. They remain in the preserved source artifact and in a version-scoped normalized source representation suitable for future re-projection.

A field being unknown does not automatically make the bundle invalid.

### 5.4 Identifier and graph rules

Within one plan version:

- source work-item IDs must be nonempty, bounded, normalized strings;
- IDs must be unique;
- required dependency references must resolve to another item in the same version unless a future explicit external-dependency form is introduced;
- self-dependencies are invalid;
- the required dependency graph must be acyclic;
- repeated required edges are invalid or deterministically deduplicated with a warning; Phase A must choose one behavior and test it;
- `recommends`, when present, is nonblocking;
- an unresolved recommended reference produces a warning, not a fatal import error;
- dependency order in the source must not change semantic identity;
- error diagnostics must identify the source artifact, work-item ID or field, machine-readable code, severity, and human-readable message.

Do not infer dependencies from Markdown prose.

### 5.5 Durable planning model

Add durable records equivalent to:

```text
Project
PlanBundle
PlanVersion
PlanImportAttempt
PlanArtifact
PlanImportDiagnostic
WorkItem
WorkItemDependency
WorkContractDraft
```

Identifiers should be branded domain IDs, including at least:

```text
PlanBundleId
PlanVersionId
PlanImportAttemptId
PlanArtifactId
PlanImportDiagnosticId
WorkContractDraftId
```

`ProjectId` and `WorkItemId` already exist and should be retained if their semantics remain correct.

All project and planning records are workspace-scoped directly or through enforced parent foreign keys.

### 5.6 Plan identity and versioning

Use these concepts:

```text
Project
    a CraftingTable project container visible to the user

PlanBundle
    the stable logical family of imported planning material

PlanVersion
    one immutable, content-addressed import result

PlanImportAttempt
    one success, failure, or idempotent-repeat attempt
```

The canonical bundle digest must include:

- normalized logical artifact roles;
- normalized logical filenames;
- exact artifact bytes;
- deterministic ordering;
- an explicit digest format version.

It must not depend on:

- multipart part order;
- upload timestamp;
- local temporary filenames;
- parser-generated IDs.

Rules:

- the first successful import creates the project, bundle, and version atomically;
- the first successful version becomes the project's active plan version;
- re-importing byte-identical logical artifacts is idempotent and returns the existing plan version;
- an idempotent repeat records an import attempt and safe audit evidence but does not duplicate artifacts, work items, dependencies, or workspace events;
- changed content creates a new immutable `PlanVersion`;
- a changed version is preserved and viewable but does not silently replace the active version;
- plan activation or version comparison beyond the initial version is deferred to Planning Studio;
- old plan versions and work items remain queryable and immutable.

### 5.7 Artifact preservation

For CT-03, store accepted planning artifacts in SQLite as bounded immutable BLOBs with:

```text
logical filename
artifact role
media type
byte length
SHA-256 content digest
exact bytes
created time
```

This is an intentional narrow decision for small planning inputs so a successful import can be one atomic database transaction.

It does not establish SQLite as CraftingTable's general large-artifact store. General execution logs, patches, transcripts, and build artifacts remain later filesystem/content-addressed scope.

Source bytes must be retrievable through an authorized endpoint. Unknown fields and comments need not survive a parse-and-reserialize operation because exact original bytes remain authoritative.

### 5.8 Import attempts and diagnostics

Every import request receives a durable `PlanImportAttempt`.

Outcomes:

```text
Succeeded
FailedValidation
Duplicate
```

A failed validation attempt must persist:

- bounded source artifacts or a safe bounded representation sufficient for diagnosis;
- diagnostics;
- actor and workspace attribution;
- request and bundle digest information where available;
- safe audit evidence.

It must not create:

- a project;
- a plan bundle;
- a plan version;
- work items;
- dependency edges;
- a work-contract draft;
- a workspace event.

A successful import must commit atomically:

```text
import attempt
+ project
+ plan bundle
+ plan version
+ artifacts
+ diagnostics
+ work items
+ dependency edges
+ audit event
+ workspace events
```

No browser-visible success may precede commit.

### 5.9 Journal vocabulary extensibility

Migration `0001-ct02-foundation.sql` uses a deliberately tiny closed vocabulary for CT-02 audit actions and workspace-event kinds.

CT-03 must add migration `0002` that makes these vocabularies migration-owned and extensible without weakening append-only history.

Preferred design:

```text
audit_action_kinds
workspace_event_kinds
```

with journal rows referencing catalog entries.

Migration `0002` must:

- preserve all CT-02 journal rows and global event sequences;
- preserve append-only no-update/no-delete triggers;
- preserve indexes and foreign-key integrity;
- seed all CT-02 and CT-03 action/event kinds;
- keep application-level strict Zod payload validation;
- prevent arbitrary unregistered action or event strings;
- permit a future migration to add a vocabulary entry without rebuilding the journals again.

A different design may be proposed in Phase A only if it provides the same long-term property and proves preservation of CT-02 data.

Initial CT-03 audit action vocabulary should include at least:

```text
plan.import.succeeded
plan.import.failed
plan.import.duplicate
work-item.admitted
work-contract-draft.created
```

Initial CT-03 workspace-event vocabulary should include at least:

```text
project-created
plan-version-imported
work-item-admitted
```

Do not emit one workspace event for every imported work item. The import event should summarize the committed version and counts.

### 5.10 Event notification

Every successful daemon transaction that appends a workspace event must:

1. commit state, audit, and event rows;
2. return successfully from the storage transaction;
3. call the daemon's composed `WorkspaceEventNotifier`;
4. allow connected streams to re-query the authoritative journal.

The notifier carries no payload and is not part of the transaction.

Acceptance tests must configure the fallback poll longer than the expected test duration and prove that:

- successful plan import reaches a connected SSE client through same-process notification;
- work-item admission reaches a connected SSE client through same-process notification;
- delivery does not wait for the fallback poll;
- a deliberately dropped notification is still recovered by the existing durable timeout/re-query behavior.

### 5.11 Work-item state and readiness

CT-03 supports these active transitions:

```text
Proposed → Admitted
```

Future status vocabulary may reserve:

```text
Active
Completed
Canceled
Superseded
```

but CT-03 must not expose unsupported transitions.

Definitions:

```text
Proposed
    imported, preserved, but not accepted into the operator's agenda

Admitted
    intentionally accepted into the agenda and paired with an
    incomplete work-contract draft
```

Admission is not execution readiness.

Required-dependency blockers are derived from the selected plan version:

```text
blocked
    one or more required predecessors are not Completed

planning-ready
    Proposed and no unsatisfied required dependencies

active
    Admitted, regardless of whether later execution prerequisites exist
```

Because CT-03 has no completion workflow, importing AQ-CONT-1 initially makes `AQ-01` the only planning-ready item and leaves its descendants **Dependency-blocked**.

UI and contracts must say **planning-ready** or **ready for admission**, not merely “ready,” where confusion with executable or merge readiness is possible.

### 5.12 Manual admission and draft contract

Only an authenticated `Owner` or `Editor` may admit a proposed item.

Admission must be idempotent.

A successful first admission atomically commits:

```text
WorkItem status → Admitted
+ one initial WorkContractDraft
+ audit rows
+ work-item-admitted workspace event
```

then notifies the live stream after commit.

The user may admit an item even when its plan dependencies are unsatisfied. The UI must show the blockers and require an explicit action; admission means “I accept this into the agenda,” not “run this now.”

The initial `WorkContractDraft` must be clearly non-executable:

```text
schemaVersion: 1
status: Draft
completeness: Incomplete
```

It should preserve or derive:

```text
project and plan-version references
source work-item ID and title
objective and exit gate
risk
primary areas
required and recommended dependencies
human merge required
default review perspectives
bounded remediation-generation default
```

It must explicitly mark unresolved fields such as:

```text
registered repository
exact base revision
writable and forbidden path scopes
verification command IDs
protected acceptance criteria
backend selection
execution environment
```

CT-03 may display structured and YAML-like draft views. It must not approve a contract, create a change request, create a worktree, or start an agent.

### 5.13 HTTP and application service shape

Use thin routes and service-layer authorization.

Expected capability surface:

```text
POST /api/workspaces/:workspaceId/plan-imports

GET  /api/workspaces/:workspaceId/projects
GET  /api/workspaces/:workspaceId/projects/:projectId
GET  /api/workspaces/:workspaceId/projects/:projectId/plan-versions/:planVersionId

GET  /api/workspaces/:workspaceId/work-items/:workItemId
POST /api/workspaces/:workspaceId/work-items/:workItemId/admit

GET  /api/workspaces/:workspaceId/plan-artifacts/:artifactId
```

The exact resource nesting may change during Phase A if authorization and identity remain unambiguous.

All returned data must use strict shared contracts and browser-side revalidation. Routes must not return raw SQLite rows.

### 5.14 Browser information architecture

CT-03 should make the imported plan understandable without becoming a full IDE or graph editor.

Required views:

```text
workspace dashboard
project list or cards
project detail
plan-version detail
work-item detail
import dialog or page
work-contract draft view
```

The workspace dashboard must replace zero-value placeholder status regions with real project/work-item summaries.

Project detail should show:

- project and active plan metadata;
- plan-version history;
- source artifact inventory;
- import diagnostics;
- risk distribution;
- proposed/admitted counts;
- planning-ready and blocked counts;
- work-item table;
- dependency and blocker summaries.

Work-item detail should show:

- source ID and title;
- plan version;
- risk and primary areas;
- exit gate;
- required and recommended dependencies;
- current blockers;
- admission status;
- an explicit admission control;
- draft-contract content after admission.

A table or list with clear dependency summaries is sufficient. Do not build an interactive graph canvas in CT-03.

Deep-linkable routes are desirable. Phase A may propose a lightweight router if it keeps the current application boundary clear and avoids broad framework churn.

### 5.15 Snapshot and event projection

Extend the workspace snapshot with enough server-derived summary data to render the dashboard honestly.

At minimum, include:

```text
project summaries
plan/import attention count
proposed work-item count
admitted work-item count
planning-ready count
blocked count
risk summary
recent activity
asOfSequence
```

Do not load every source artifact into the workspace snapshot.

On relevant workspace events, the browser should invalidate or refetch affected snapshots/details rather than treating event payloads as the authoritative complete model.

The SSE journal remains an activity and invalidation stream. SQLite-backed queries remain the authoritative projection.

### 5.16 Security and disclosure

Planning files are untrusted input.

The implementation must:

- parse YAML with a library/configuration that does not construct arbitrary executable objects;
- bound aliases, nesting, size, and resource consumption where the selected parser permits;
- render all source text as text, never raw HTML;
- prevent Markdown from executing scripts or loading remote content;
- validate JSON/YAML/Markdown media and artifact roles;
- avoid logging complete source artifacts by default;
- prevent cross-workspace artifact and diagnostic reads;
- keep failed-import diagnostics free of secrets such as session tokens and headers;
- preserve existing CSRF, origin, session, and workspace authorization behavior;
- remain loopback-only.

Do not add arbitrary file-path import from the browser or daemon.

## 7. Required invariants

```text
CT03-I01  Import never executes work.

CT03-I02  A faculty, model, parser, or source document cannot silently
          broaden authorization or mark work executable.

CT03-I03  Exact source artifact bytes remain retrievable and immutable.

CT03-I04  One successful import is one atomic planning transition.

CT03-I05  A failed import creates no project, plan version, work item,
          dependency, draft contract, or workspace event.

CT03-I06  An identical import is idempotent.

CT03-I07  Changed content creates a new immutable version and does not
          silently replace the active version.

CT03-I08  Required dependency graphs are complete and acyclic.

CT03-I09  Recommended edges never become blocking authority.

CT03-I10  Work-item admission is explicit, attributable, idempotent,
          and distinct from execution readiness.

CT03-I11  A work-contract draft is visibly incomplete and non-executable.

CT03-I12  Every daemon-side event-producing command notifies only after
          commit and never uses the notifier as storage.

CT03-I13  Browser state is rebuilt from authorized queries plus durable
          cursor events, not from local optimistic authority.

CT03-I14  Workspace isolation applies to plans, artifacts, diagnostics,
          work items, drafts, audit rows, events, and summaries.

CT03-I15  Journals remain append-only across migration 0002.

CT03-I16  Unknown planning fields are preserved rather than discarded.

CT03-I17  No CT-04-or-later capability enters the runtime.
```

## 10. Exit gate

CT-03 is complete only when all of the following are true:

```text
the exact AQ-CONT-1 fixture imports without losing source fields

AQ-01 through AQ-14 appear in one immutable plan version

all 24 required dependency edges are represented

AQ-01 is the only initially planning-ready root item

risk, dependency, blocker, and status summaries are correct

an authenticated operator can inspect project, plan, and work-item pages

AQ-01 can be explicitly admitted

admission creates one clearly incomplete, non-executable draft contract

successful import and admission reach connected SSE clients through
post-commit notifier delivery without waiting for fallback polling

refresh and daemon restart preserve imported plans and admission state

a duplicate import does not duplicate durable planning state

a changed import creates a distinct immutable version without silently
changing the active version

invalid IDs, missing dependencies, self-dependencies, duplicate IDs,
and cycles fail with actionable persisted diagnostics

failed imports produce no partial project or workspace-event state

all CT-01 and CT-02 regression gates remain green

the literal root pnpm check passes under the pinned runtime
```

## 11. Stop conditions

Stop and request operator judgment rather than guessing if:

- the source contradicts a fixed work-contract decision;
- supporting the AQ fixture requires repository or Git behavior;
- a required artifact role cannot be identified without heuristic prose interpretation;
- a schema change would weaken journal immutability or workspace isolation;
- the importer would need to execute source content;
- an import cannot be made atomic with the proposed persistence model;
- implementing a requested UI would require CT-04-or-later capabilities;
- the accepted planning schema is materially insufficient and needs a contract amendment.

Do not weaken acceptance criteria or edit fixtures to make an implementation pass.
