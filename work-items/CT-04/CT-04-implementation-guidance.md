# CT-04 implementation guidance

## 1. Purpose

This document proposes a source-specific implementation shape for CT-04. It is not permission to skip the slice-level Phase A and design-review process. Each slice must reconcile these recommendations against the actual source before implementation.

## 2. Dependency direction

Target logical dependencies:

```text
domain        → none
contracts     → domain
planning      → domain
git           → domain + Node process/filesystem primitives
artifacts     → domain + Node filesystem primitives
storage       → domain
server        → domain + contracts + planning + git + artifacts + storage
web           → domain + contracts
```

`git` must not import Fastify, React, SQLite, storage repositories, workspace membership, audit, or event publishing.

`artifacts` must not import Fastify, React, SQLite, Git, or workspace policy. It accepts server-generated bytes and returns immutable content descriptors.

Only the server layer coordinates authorization, storage transactions, Git effects, artifact publication, audit, events, and notifier calls.

## 4. Configuration

Recommended daemon configuration:

```text
CRAFTINGTABLE_REPOSITORY_ROOTS
    colon-separated or repeated absolute source roots

CRAFTINGTABLE_WORKTREE_ROOT
    absolute daemon-managed root

CRAFTINGTABLE_ARTIFACT_ROOT
    absolute content-addressed artifact root

CRAFTINGTABLE_GIT_BIN
    absolute or startup-resolved Git executable

CRAFTINGTABLE_GIT_TIMEOUT_MS
CRAFTINGTABLE_GIT_STDOUT_LIMIT_BYTES
CRAFTINGTABLE_GIT_STDERR_LIMIT_BYTES
CRAFTINGTABLE_DIFF_LIMIT_BYTES
CRAFTINGTABLE_UNTRACKED_FILE_LIMIT_BYTES
CRAFTINGTABLE_DIFF_FILE_COUNT_LIMIT
```

Startup must canonicalize roots and reject unsafe overlap:

```text
data root overlaps a repository root
worktree root overlaps a repository root
artifact root overlaps a repository root
source roots overlap one another ambiguously
nonexistent or non-directory roots
world-writable roots when policy forbids them
```

The accepted Phase A plan must state the exact overlap rules and tests.

## 5. Typed Git command runner

The runner should expose internal operation-specific functions, not a public `run(args: string[])` to routes or contracts.

A low-level private runner may accept a typed command description:

```ts
interface GitInvocation {
  readonly executable: AbsolutePath;
  readonly cwd: AbsolutePath;
  readonly operation: GitOperationKind;
  readonly args: readonly string[];
  readonly timeoutMs: number;
  readonly stdoutLimit: number;
  readonly stderrLimit: number;
  readonly environmentProfile: GitEnvironmentProfile;
}
```

Only package-owned code constructs it.

Use `spawn`, not a shell. Reject arguments containing NUL. Treat any user-originated value as data at a fixed argument position, never as a subcommand or option. Use `--` when the Git command supports it.

Sanitize inherited environment variables, including:

```text
GIT_DIR
GIT_WORK_TREE
GIT_INDEX_FILE
GIT_OBJECT_DIRECTORY
GIT_ALTERNATE_OBJECT_DIRECTORIES
GIT_CONFIG
GIT_CONFIG_COUNT
GIT_CONFIG_KEY_*
GIT_CONFIG_VALUE_*
GIT_EXEC_PATH
GIT_CEILING_DIRECTORIES
GIT_SSH
GIT_SSH_COMMAND
GIT_ASKPASS
SSH_ASKPASS
```

Then set explicit noninteractive and deterministic values.

The runner returns structured evidence:

```text
exit code
terminating signal
timed out
stdout bytes or overflow classification
stderr bytes or overflow classification
started / finished time
invocation policy version
```

It never logs secrets, full environment, or unbounded output.

## 6. Repository registration algorithm

Recommended order:

```text
1. Authorize Owner in workspace.
2. Validate request schema and display name.
3. Resolve requested path lexically against no implicit cwd.
4. Require absolute input.
5. Verify it lies below one configured source root.
6. Reject any symlink component or resolve-and-compare according to the accepted policy.
7. `realpath` the path.
8. Run bounded read-only Git inspection.
9. Require non-bare primary worktree and exact top-level equality.
10. Resolve canonical Git common directory and object format.
11. Collect filesystem identity evidence with `stat`, where supported.
12. Inspect known external-execution configuration/features and record policy result.
13. Re-check path identity immediately before the transaction.
14. Atomically store repository + audit + workspace event.
15. Commit.
16. Notify.
```

Never infer a repository from a project name or plan metadata.

## 7. Repository identity revalidation

Before every Git effect or evidence capture:

```text
realpath current registered path
stat current top-level
Git rev-parse current top-level/common-dir/object-format
compare with registration record
```

If identity differs:

```text
mark repository identity-mismatch
record audit + workspace event
block the requested operation
require explicit Owner re-registration or retirement
```

Do not automatically update the canonical path or filesystem identity.

## 8. Change-request construction

Recommended workflow:

```text
1. Authorize Owner or Editor.
2. Load admitted work item and its exact current draft.
3. Load same-workspace project binding and active repository.
4. Revalidate repository identity.
5. Validate configured target ref against repository policy.
6. Resolve target ref to full commit SHA using `^{commit}`.
7. If caller supplies a base SHA, require exact equality with the resolved commit unless policy explicitly supports historical bases.
8. Optionally prove base is reachable from the target ref.
9. Generate a branch name from server-owned IDs under the repository prefix.
10. Check ref format and collision.
11. Atomically store ChangeRequest + audit + event.
12. Commit and notify.
```

The first release should usually use the current local target-ref commit as the exact base. Supporting arbitrary historical bases increases stale-base and reachability policy and should be proposed explicitly.

## 9. Worktree side-effect protocol

Provisioning should be modeled as:

```text
transaction A
    ChangeRequest → provisioning
    insert GitOperation(planned)
    audit + event
commit
notify

transaction B
    GitOperation → running
commit

execute one bounded `git worktree add -b ...`

inspect repository state

transaction C
    operation outcome
    managed worktree
    open generation placeholder
    ChangeRequest → provisioned or blocked/failed/uncertain
    audit + event
commit
notify
```

A crash can occur between any arrows. Startup reconciliation inspects:

```text
branch existence and exact tip
Git worktree registry
expected managed path
filesystem directory identity
worktree HEAD and branch
```

Recommended reconciliation matrix:

```text
no branch, no registered worktree, no directory
    safe to retry only through explicit resume

expected branch at exact base, no worktree, no directory
    recognized partial state; resume using existing branch after approval/policy

expected registered worktree at exact path, branch, and HEAD
    mark provisioned/reconciled

branch exists at wrong tip
    blocked

expected path exists but is not registered worktree
    blocked; never delete

registered worktree path differs from expected
    blocked

worktree registered but directory missing
    blocked; no automatic prune in CT-04
```

Blindly rerunning `-b` is not reconciliation.

## 10. Concurrency

At minimum:

- one active provision/remove operation per registered repository;
- one active managed worktree per change request;
- one open change request per admitted work item in CT-04;
- database uniqueness constraints for durable exclusion;
- a process-local repository mutex to reduce expected contention;
- database constraints and reconciliation remain authoritative after restart.

Do not rely only on an in-memory lock.

## 11. Cleanup protocol

Recommended order:

```text
1. Authorize Owner or Editor.
2. Load exact managed worktree and repository.
3. Revalidate source repository identity.
4. Verify worktree is listed at exact expected path.
5. Verify exact expected branch.
6. Verify HEAD and branch identity are coherent.
7. Capture status with NUL-safe parser.
8. Reject staged, unstaged, untracked, conflicted, or unsupported state.
9. Commit remove-worktree operation intent.
10. Run bounded `git worktree remove` without `--force`.
11. Inspect actual state.
12. Commit outcome and event.
```

Never fall back to `rm -rf`. Never delete the branch in CT-04.

## 12. Artifact store

Recommended layout:

```text
<artifact-root>/sha256/ab/cd/<full-hash>
```

Publish algorithm:

```text
stream bytes to random temporary file under artifact root
bound size while writing
hash while writing
fsync file
rename with no replacement to final content path
fsync parent directory
return hash / size / media type
then commit SQLite metadata reference
```

If the content already exists at the final hash, verify size/hash and reuse it.

A crash before metadata commit may leave an orphan. CT-04 does not need garbage collection. A metadata row must never be committed before the final artifact bytes exist.

Read algorithm:

```text
resolve metadata by opaque artifact ID and authorized parent join
construct path only from validated stored hash
open without following user-provided path
bound response
verify hash, at least in tests and on detected corruption policy
serve as text/plain or octet-stream with nosniff and restrictive CSP
```

## 13. Status and diff capture

Use NUL-delimited porcelain output:

```text
git status --porcelain=v2 -z --branch --untracked-files=all
```

The parser should operate on `Buffer`, not newline-split text. It must explicitly validate UTF-8 before serializing a path into JSON. Unsupported path encoding blocks a complete snapshot and produces a structured diagnostic.

Capture separate evidence for:

```text
staged tracked changes
unstaged tracked changes
untracked files
conflicts
submodules
unsupported/special files
```

Tracked patch commands must disable external diff and textconv and set fixed prefixes/full indexes. Do not assume one combined patch is unambiguous when a file has both staged and unstaged changes.

For untracked entries:

- resolve only beneath the exact managed worktree;
- `lstat` without following symlinks;
- regular files may be read under a per-file and total limit;
- symlink targets may be recorded as bounded text without following;
- directories are represented through contained status entries;
- sockets, devices, FIFOs, or other special files are marked unsupported;
- binary files are classified and not rendered as text;
- submodules are represented, not recursively inspected.

If any output limit is reached, mark the snapshot `truncated` or `incomplete`; do not present partial bytes as complete evidence.

## 14. Browser design

The first UI is a supervisory review surface, not an IDE.

Recommended routes:

```text
/workspaces/:workspaceId/repositories
/workspaces/:workspaceId/repositories/:repositoryId
/workspaces/:workspaceId/projects/:projectId/work-items/:workItemId
/workspaces/:workspaceId/change-requests/:changeRequestId
/workspaces/:workspaceId/change-requests/:changeRequestId/diffs/:diffSnapshotId
```

A work-item page may add a “Prepare change request” panel only when:

```text
work item is Admitted
project has one active repository binding
no open change request already exists
```

The change-request page should show:

```text
project and work item
repository identity and status
target ref
exact base SHA
task branch
worktree path as read-only daemon state
worktree/operation state
current status summary
latest diff snapshot
explicit non-readiness notice
```

The diff view should show a file/status list plus safe unified text. No `dangerouslySetInnerHTML`, remote content, arbitrary file fetch, or terminal.

All asynchronous responses must be keyed to captured workspace and resource identity. Use abort signals where practical, but identity comparison remains required because cancellation is not guaranteed.

## 15. Test fixture strategy

Create a fixture factory that builds temporary repositories without network access:

```text
primary repository with initial commit and main branch
second commit for base/ref tests
bare repository
linked worktree path
repository under symlinked component
nested repository
repository with branch collision
repository with malicious-looking filenames
repository with staged, unstaged, untracked, binary, symlink, and conflict states
repository with configured hooks/external diff/textconv/fsmonitor/filter features
```

Tests must use the same Git executable policy as production. Do not replace all Git behavior with mocks; pure parsers can use fixtures, but worktree and crash semantics need real temporary repositories.

## 16. Documentation and ADRs

Expected ADR subjects:

```text
Git process boundary and repository trust
canonical repository identity and allowed roots
change-request and exact-base identity
crash-reconciled worktree operations
content-addressed local artifacts
status/diff evidence semantics
```

One ADR may cover more than one subject if the decision remains coherent. Do not create an ADR for routine file layout.

## 17. Slice completion discipline

Each slice completion report must include:

```text
contract and accepted plan references
base SHA and implementation head SHA
migration(s) added
public API/route changes
Git subcommands introduced
all deterministic commands run
protected acceptance IDs exercised
adversarial matrix coverage
known limitations
scope diff against the slice contract
```

The report must derive its head SHA after the implementation commit exists or be amended in a separate record commit. Do not claim a future SHA.
