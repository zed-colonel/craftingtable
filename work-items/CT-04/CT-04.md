# CT-04 — Controlled repositories, change requests, worktrees, and diff evidence

**Risk:** High  
**Dependencies:** CT-02, CT-03  
**Status:** Parent milestone proposed for operator approval  
**Source baseline:** `abc5f37815ad76430cae989224afde817d77a047` (`Merge CT-03: plan import and dashboard into main`)  
**Primary areas:** Git process boundary, repository registration, project binding, change requests, worktrees, Git-operation recovery, immutable diff evidence, browser review surface

## 1. Objective

Extend the accepted CT-03 planning and admission control plane so an admitted work item can be bound to one explicitly registered local Git repository, one exact base commit, one controlled task branch, and one daemon-managed worktree. CraftingTable must then capture an immutable, bounded view of the worktree's status and changes and present that evidence in the browser.

The first end-to-end acceptance workload is the admitted `AQ-01` work item against the operator's local ActionQueue repository.

CT-04 must establish:

- a trusted, typed Git process boundary with no generic shell interface;
- explicit, workspace-owned repository registration under configured host roots;
- canonical repository identity and replacement detection;
- project-to-repository binding that cannot cross workspaces or projects;
- exact-base `ChangeRequest` identity, with a server-generated branch name;
- durable Git-operation intents recorded before host-side side effects;
- crash reconciliation for worktree creation and cleanup;
- managed worktree paths that are never supplied by the browser;
- safe dirty-worktree and identity checks before cleanup;
- a minimal open `Generation` placeholder that carries no verification or merge meaning;
- immutable status and diff snapshots tied to exact repository/worktree state;
- a bounded content-addressed filesystem artifact seam for diff evidence;
- a browser surface for repositories, change requests, worktree state, file status, and unified diff evidence;
- no arbitrary path, argument-vector, command, or remote-Git endpoint.

CT-04 does **not** start coding agents, run repository checks, create generation commits, review changes, decide readiness, or merge branches.

## 2. Governing statements

> Registering a repository is an explicit grant to inspect and manipulate one operator-owned Git worktree domain. A path string is not authority.

> A change request fixes purpose, repository, target ref, exact base commit, and branch identity before a worktree exists.

> A Git subprocess is a host-side effect. Its intent is durable before execution, and an interrupted result is reconciled from observable repository state rather than guessed.

> A diff snapshot is immutable evidence about one exact observed worktree state. It is not proof that work is complete, reviewed, or safe to merge.

## 4. Accepted CT-03 foundation

CT-04 must extend, not bypass, these properties:

- one loopback-only authenticated Fastify daemon;
- one authoritative SQLite database with ordered checksum-verified migrations;
- pure branded domain identifiers and records;
- strict Zod wire contracts validated by server and browser;
- service-layer workspace authorization;
- structural workspace/project/version ownership enforced by composite keys and triggers;
- append-only audit and workspace-event journals;
- atomic state, audit, and related workspace-event transactions;
- post-commit notifier delivery plus durable SSE re-query;
- snapshot-first browser reconstruction with a global event cursor;
- immutable imported plan history;
- one terminal `Proposed → Admitted` work-item transition;
- an admitted work item's deliberately incomplete, non-executable `WorkContractDraft`;
- no ActionQueue, WorldInterface, Exoskeleton, vendor-agent, or generic process dependency.

CT-04 may resolve only these CT-03 draft fields:

```text
registered-repository
exact-base-revision
```

It may introduce structural placeholders for path scope and verification policy, but it must not claim those fields are approved or executable unless their governing work item explicitly implements them. Agent backend and execution environment remain unresolved.

## 6. Common domain vocabulary

The exact TypeScript shape may be refined during reviewed Phase A plans, but these meanings are fixed.

### 6.1 RegisteredRepository

A workspace-owned record binding a stable CraftingTable ID to an operator-approved canonical Git top-level.

It records at minimum:

```text
repository ID
workspace ID
display name
canonical top-level path
canonical Git common directory
filesystem identity evidence where supported
Git object format
registration policy version
registered by / registered at
status: active | identity-mismatch | unavailable | retired
```

A browser-supplied path is merely a registration request. The daemon establishes the authoritative canonical identity.

The same canonical physical repository may not be actively registered to two workspaces in CT-04. Sharing is a future explicit feature.

### 6.2 RepositoryPolicy

A structural policy attached to a registered repository. CT-04 needs only the fields required for its own operations:

```text
allowed target refs
CraftingTable branch prefix
worktree root policy
status/diff size limits
whether submodules may be represented
whether repository-configured external execution features were detected
```

Repository policy is not a future verification policy and does not authorize arbitrary commands.

### 6.3 ProjectRepositoryBinding

An explicit same-workspace relationship between one CraftingTable project and one registered repository. Project names, repository directory names, or plan prose must never create an implicit binding.

### 6.4 ChangeRequest

A durable local-PR analogue that binds:

```text
workspace
project
admitted work item
work-contract draft version
registered repository
configured target ref
exact base commit SHA
server-generated task branch
state and version
```

A `ChangeRequest` is not an agent run and is not merge-ready.

### 6.5 GitOperation

A durable intent and outcome record for a bounded typed Git side effect.

```text
kind: provision-worktree | remove-worktree | refresh-diff
state: planned | running | succeeded | failed | uncertain | blocked | reconciled
input digest
expected repository / branch / path / base
observed outcome evidence
started / finished / reconciled timestamps
```

The operation exists before the subprocess begins. A daemon restart never converts `running` to `failed` by assumption; it reconciles observable state.

### 6.6 ManagedWorktree

A daemon-owned binding among one `ChangeRequest`, one generated filesystem path below the configured worktree root, one branch, and one observed `HEAD`.

No browser route accepts a worktree path. No worktree record may point outside the configured root.

### 6.7 Generation placeholder

CT-04 may create one open generation placeholder when a worktree becomes managed:

```text
ordinal: 1
state: open
opened at
change request / worktree identity
```

It has no generation commit, checks, review, completion, readiness, or merge semantics. Those remain CT-06 and later.

### 6.8 DiffSnapshot

An immutable observation tied to:

```text
workspace / project / change request / worktree
repository identity snapshot
base SHA
observed worktree HEAD SHA
status manifest hash
staged patch artifact, if present
unstaged patch artifact, if present
bounded untracked-file evidence
truncation / unsupported-content flags
captured by / captured at
```

A later refresh creates another snapshot. It never updates an earlier one.

## 7. Cross-slice invariants

### CT04-I01 — No generic shell

No browser, HTTP contract, domain type, or service accepts an arbitrary command string or arbitrary argument vector. Only named typed Git operations exist.

### CT04-I02 — No remote Git

CT-04 does not clone, fetch, pull, push, contact remotes, invoke credential helpers, or prompt for credentials.

### CT04-I03 — Registration is privileged

Only an authenticated `Owner` may introduce a new host path. Editors may operate repositories already admitted to their workspace; viewers are read-only.

### CT04-I04 — Canonical identity precedes storage

A repository is stored only after the daemon proves that the requested path resolves to an existing, non-bare primary Git worktree inside or equal to an allowed source root and outside CraftingTable's data and managed-worktree roots.

### CT04-I05 — Repository replacement is detected

Every mutating or evidence-producing operation revalidates the registered repository identity. A path that now names a different repository is blocked, not silently accepted.

### CT04-I06 — Physical repositories do not cross workspaces

One canonical repository identity cannot be actively registered to two workspaces in CT-04.

### CT04-I07 — Ownership is structural

Repository, project binding, work item, contract draft, change request, operation, worktree, generation, artifact metadata, and diff snapshot relationships reject cross-workspace and same-workspace/wrong-parent combinations at the database boundary.

### CT04-I08 — Exact base means exact commit

A change request stores a full commit object ID resolved as a commit. A symbolic ref, abbreviated SHA, tag object, tree, blob, or caller description is not accepted as the authoritative base.

### CT04-I09 — Base and target ref are distinct facts

The configured target ref explains where the work is intended eventually to integrate. The exact base SHA defines the starting content. Both are stored and displayed.

### CT04-I10 — Branch identity is server generated

The browser cannot choose arbitrary branch names. The daemon generates a bounded name under a configured CraftingTable prefix and validates it with Git's ref-format rules.

### CT04-I11 — Side-effect intent is durable first

A `GitOperation` and related audit record are committed before `git worktree add` or `git worktree remove` begins.

### CT04-I12 — Unknown outcomes are reconciled

Process loss, daemon crash, timeout, or ambiguous subprocess termination produces `uncertain` or `blocked`, followed by observation-based reconciliation. It does not produce blind retry or blind cleanup.

### CT04-I13 — Worktree paths are generated

Managed paths derive only from configured roots and server-owned IDs. A user cannot supply or modify the path.

### CT04-I14 — Cleanup fails closed

Cleanup refuses a dirty worktree, an unexpected branch, an unexpected `HEAD`, an identity mismatch, an unregistered path, or a directory that is not the exact managed worktree. No recursive deletion fallback exists.

### CT04-I15 — Branch deletion is deferred

CT-04 worktree cleanup removes only the managed worktree. It does not automatically delete the task branch. Branch lifecycle belongs to later merge/cleanup policy.

### CT04-I16 — Git environment is bounded

Git subprocesses use fixed binaries, fixed subcommands, argument arrays, bounded outputs and deadlines, no terminal prompts, no pagers, disabled hooks where possible, and command-specific suppression of external diff/textconv/fsmonitor behavior.

### CT04-I17 — Repository trust is explicit

Registration is an operator trust decision for a local repository. CT-04 does not claim that a Git checkout can safely process an actively malicious repository configuration; it detects and reports known external-execution features and never treats registration as safe for mutually untrusted code.

### CT04-I18 — Evidence is immutable

Artifacts and diff snapshots are content-addressed or otherwise immutable. A current snapshot is a pointer to a new record, not an update to historical evidence.

### CT04-I19 — Durable artifact bytes precede metadata

For filesystem-backed artifacts, bytes are written, fsynced, hashed, and atomically published before SQLite metadata references them. A crash may leave an unreferenced orphan, never a committed metadata row pointing to absent bytes.

### CT04-I20 — Diff capture is NUL-safe and bounded

Status parsing uses NUL-delimited machine output. Non-UTF-8 paths, special files, submodules, binary data, and output-limit conditions are classified explicitly rather than silently misparsed.

### CT04-I21 — External renderers are disabled

Diff capture does not invoke repository-configured external diff commands, textconv, pagers, or interactive tools.

### CT04-I22 — Browser state is resource keyed

Repository, change-request, worktree, and diff responses are applied only if the current workspace and route identity still match the request that produced them. Late success and failure from a previous workspace or route cannot populate or clear the current view.

### CT04-I23 — Events follow commit

Commands that append workspace events call the composed notifier only after their authoritative transaction commits. The durable journal remains the source of truth.

### CT04-I24 — Operation facts are not readiness

A provisioned worktree, clean status, or empty diff does not mean a work contract is approved, an agent is complete, checks passed, review occurred, or merge is authorized.

### CT04-I25 — Protected acceptance remains independent

The implementation may read the protected acceptance specification but may not change it. Any change requires a separate operator-approved contract amendment.

## 8. Common authorization model

| Operation | Owner | Editor | Viewer |
|---|---:|---:|---:|
| Register or retire a host repository path | Yes | No | No |
| Bind an already registered repository to a project | Yes | Yes | No |
| Create a change request | Yes | Yes | No |
| Provision or refresh a managed worktree | Yes | Yes | No |
| Capture status/diff evidence | Yes | Yes | Read existing only |
| Request safe worktree cleanup | Yes | Yes | No |
| View repository/change-request/diff state | Yes | Yes | Yes |

Every operation still performs service-layer membership authorization and structural ownership checks. UI visibility is not authorization.

## 9. Git command policy

The implementation must use a fixed executable resolved by configuration or startup validation. It must never execute a shell command constructed by concatenation.

The Phase A plan must enumerate every Git subcommand introduced by its slice. At parent completion the expected command classes are limited to:

```text
version
rev-parse
show-ref / for-each-ref
check-ref-format
status --porcelain=v2 -z
worktree list --porcelain -z
worktree add
worktree remove
diff with --no-ext-diff and --no-textconv
config inspection limited to fixed keys/regexes
```

A material expansion requires operator approval.

The subprocess environment must at least:

```text
set GIT_TERMINAL_PROMPT=0
set GIT_PAGER=cat
set PAGER=cat
set LC_ALL=C
remove inherited Git directory/worktree/index overrides
use argument arrays
bound stdout/stderr bytes
bound wall time
record exit/signal/timeout classification
```

Commands that can check out files must override hooks to a disabled path. Read/evidence commands must disable fsmonitor, external diffs, and textconv where applicable.

## 10. Common persistence rules

Each slice introduces its own ordered migration rather than one milestone-wide migration:

```text
CT-04A  repository registration and project binding
CT-04B  change requests and branch/base identity
CT-04C  Git operations, managed worktrees, open generation placeholder
CT-04D  artifact metadata and immutable diff snapshots
CT-04E  no new schema unless the accepted Phase A design proves it necessary
```

Every migration must:

- retain all CT-02 and CT-03 rows;
- retain global workspace-event sequence values;
- preserve append-only triggers and vocabulary catalogs;
- introduce its own ownership constraints and immutability/update rules;
- pass migration replay from a fresh database and from the accepted CT-03 schema;
- fail checksum drift.

## 11. Common audit and event vocabulary

Audit and workspace-event kinds must be registered through the CT-03 catalogs. Candidate semantic kinds include:

```text
repository.register
repository.identity-mismatch
repository.bind-project
change-request.create
change-request.provision-requested
worktree.provisioned
worktree.cleanup-blocked
worktree.removed
diff-snapshot.captured
```

Do not emit one event per Git subprocess line or per changed file. Raw operational details belong in bounded operation evidence, not the primary workspace activity journal.

## 12. Parent non-goals

CT-04 must not implement:

- coding-agent adapters or agent execution;
- arbitrary process execution;
- shell or terminal access;
- repository cloning, network fetch, pull, push, or remote PR creation;
- check-policy execution;
- protected acceptance runner execution;
- controller-owned commits;
- staged-hunk editing;
- agent or human code-review findings;
- remediation loops;
- readiness or merge policy;
- rebasing, merging, cherry-picking, reset, stash, or branch deletion;
- multi-repository change requests;
- submodule recursion;
- LAN exposure, TLS, or `systemd` packaging;
- Exo Stack runtime dependencies.

## 13. Parent exit gate

CT-04 is complete only when all five slices are accepted and the following is true:

```text
AQ-01 is bound to the explicitly registered local ActionQueue repository.
The configured target ref and exact base SHA are visible.
A server-generated branch and managed worktree exist under the configured root.
The daemon can restart and reconcile the worktree without duplication.
A bounded immutable status/diff snapshot appears in the browser.
Unsafe repository paths are rejected.
Dirty, mismatched, unknown, or replaced worktrees cannot be cleaned up.
No endpoint can execute an arbitrary command or contact a Git remote.
Every accepted slice has independent design and exact-SHA code review evidence.
```
